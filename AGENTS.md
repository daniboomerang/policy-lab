# Policy Lab: agent instructions

This is the canonical instruction file for every coding agent working in this repo (Codex, Claude Code, others). `CLAUDE.md` imports it. Tool-specific files only add to it and never repeat it.

## What this is

**Policy Lab: spending policies for AI agents, drafted, tested and published.** The Policies tab of an agent-spend console, built against Saifuro's public API reference. A policy is a reusable, named set of mandate terms, assigned to agents; each assignment is saved as one Saifuro mandate. A finance controller drafts a policy in plain words with an assistant, replays the last 30 days of sample decisions against the draft, reviews the change in plain words, and publishes a new version. Every page is honest about what it is: **not connected to Saifuro, no Saifuro keys, no live calls, sample data, clearly labelled.**

This is a portfolio demo. The quality bar is production quality: craft, performance, accessibility and clean architecture all count. Read [SPEC.md](SPEC.md) before starting any task, and use the vocabulary in [CONTEXT.md](CONTEXT.md). Code, commits and PRs use its terms, not the *Avoid* alternatives.

## Stack

- **Next.js App Router** (React 19, Turbopack, server components, route handlers)
- **TypeScript**, strict, with `noUncheckedIndexedAccess`
- **Tailwind CSS v4** with **shadcn/ui**, Base UI flavour (`components.json`: style `base-nova`, base `base`). The tokens are shadcn's standard CSS variables plus `success` and `warning`, light and dark, in `src/styles/app.css`, set to Saifuro's console palette. That file is the whole token set.
- **Components come from shadcn's Base UI flavour** (`bunx shadcn@4.23.0 add <name>`), land in `src/components/ui/`, and are built on **Base UI** (`@base-ui/react`). **Only add a component when a screen needs it.** The bootstrap installs none.
- **`/system` is the component playground**: every component the app actually uses, in each of its states, on fixture data, in both themes. A component the app doesn't use is not on `/system` and not in the repo. Adding or changing a component updates its `/system` section in the same PR.
- **One data table**: every table in the app is shadcn's **Data Table**: TanStack Table (`@tanstack/react-table` 8.21, the API shadcn's guide uses) driving shadcn's `Table` component, as in shadcn's tasks example. One shared `DataTable` component, columns per screen; no other table.
- **Responsive down to 390px wide.** Every screen works at 390px with no horizontal page scroll; wide tables scroll inside their own container.
- **TanStack Query** on the client
- **openapi-typescript**: Saifuro's types are generated from the vendored OpenAPI snapshot `spec/saifuro-openapi.yaml` into `src/saifuro/schema.d.ts`
- **Biome 2.5** for linting and formatting (`biome.json`)
- **Vitest** for tests. The default environment is node. Component tests start with `// @vitest-environment happy-dom` and use Testing Library (`@testing-library/react`, `user-event`, and `jest-dom` matchers loaded in `src/test/setup.ts`).
- Package manager: **bun**

Versions are pinned exactly in `package.json`: Next.js 16.4, React 19.3, Tailwind 4.3, TypeScript 6.0, Base UI 1.9, shadcn 4.23 (CLI and its `tailwind.css`), TanStack Query 5.105, TanStack Table 8.21, openapi-typescript 7.13, Vitest 5.0, happy-dom 21, Testing Library 16, Biome 2.5.14. `shadcn add` writes dependency ranges; pin each one exactly in the same PR. Follow the installed versions' APIs, not memory: Next.js and Base UI have both changed shape across releases (Base UI's package was renamed from `@base-ui-components/react`). `src/saifuro/schema.d.ts` is generated by `bun run gen:types`: commit it, never edit it by hand. `next-env.d.ts` is written by Next.js and gitignored.

## Tooling and CI

- **Biome** (`biome.json`):
  - recommended preset;
  - 2-space indent, 120 columns, double quotes;
  - organised imports and Tailwind directives parsed in CSS;
  - `design/`, `spec/`, the generated `src/saifuro/schema.d.ts` and `next-env.d.ts`, and the Vinaya-managed `.mcp.json` and `vinaya.config.json` excluded (Vinaya rewrites both in its own formatting on `init` and `upgrade`, and `vinaya doctor` compares `.mcp.json` byte for byte, so Biome must not reformat them).
- **Import ban:** `noRestrictedImports` bans `@base-ui/react`, every `@base-ui/react/*` subpath and the old `@base-ui-components/react` name everywhere except `src/components/ui/**`. This is a lint error, not a convention.
- **`console.log` is a warning,** and CI treats warnings as errors. `console.warn` and `console.error` are allowed.
- **CI** is `.github/workflows/checks.yml`, kept deliberately light. It runs on every PR and every push to `main`, with three parallel checks:
  - **Check format** (Biome)
  - **Check lint** (Biome, warnings count as errors)
  - **Check types** (`next typegen`, then TypeScript)

  An aggregate job named `checks` passes only when all three pass. It's the one check branch protection should require.
- **Vinaya's generated workflows** (`vinaya-*.yml`) run alongside it after install.
- **Before pushing:** run `bun run fix`, then `bun run check`.

## Commands

Every task must leave these green.

- `bun dev`: dev server on port 3000
- `bun run gen:types`: regenerate `src/saifuro/schema.d.ts` from `spec/saifuro-openapi.yaml`
- `bun run check:format`: `biome format .`
- `bun run check:lint`: `biome lint --error-on-warnings .`
- `bun run check:types`: `next typegen && tsc --noEmit`
- `bun run check`: all three, the same as CI
- `bun run fix`: `biome check --write .` (formats and organises imports; run it after every `shadcn add`)
- `bun run test`: Vitest. Use `bun run test`, not bare `bun test`: bare `bun test` runs Bun's own test runner, which has no happy-dom environment and skips `vitest.config.ts`.
- `bun run build`: production build. Once `/dev-stats` lands it becomes, as in Onchain Rewind: write the development snapshot, `next build`, then the snapshot leak check (ADR-0008).

## Rules

1. **No Saifuro calls, no Saifuro keys.** No request reaches `api.saifuro.com`, and nothing reads a Saifuro key (`sk_*`, `ak_*`), in code, tests, scripts or CI. Saifuro data is read and written only through `src/saifuro/client.ts`, whose transport is `mockFetch` (ADR-0009); never pass it the global `fetch`. Every Saifuro-shaped object is sample data (fixtures in tests and on `/system`), and the UI says so: the honesty badge "Demo · sample data · not connected to Saifuro" is in the chrome of every page (ADR-0001). Agents never fetch the live OpenAPI or docs during a task; the vendored snapshot is the contract.
2. **Saifuro types come only from the generated schema.** Import Saifuro shapes from `src/saifuro/types.ts`, which aliases `schema.d.ts`. Never retype a Saifuro field by hand. A schema change is a new vendored snapshot plus `bun run gen:types` in the same PR (ADR-0002).
3. **Components read view models from the engine, never raw API shapes.** Components never import `src/saifuro/schema.d.ts` or render a `Mandate` or `Decision` directly. Mapping, evaluation and simulation live in `src/engine/` as pure, unit-tested functions (ADR-0004). The one exception is the JSON view, which shows the exact mandate bodies, and it gets them from the engine too.
4. **shadcn components in `src/components/ui/`, and no raw Base UI imports outside it.** Components come from shadcn's Base UI flavour, added with the CLI only when a screen needs one; feature code imports them from `@/components/ui/*`. Base UI composes through its `render` prop, never `asChild`. Run `bun run fix` after `shadcn add`.
5. **React 19 idioms.** `ref` is a normal prop: no `forwardRef`. Use `use()` for context.
6. **Tokens only, no extra colours.** Colours come only from shadcn's variables in `src/styles/app.css` (`background` … `chart-5`, plus `success` and `warning`) through their Tailwind utilities, and sizes, radii and type from Tailwind's default scale. No raw hex, no arbitrary values (`bg-[#…]`, `text-[13px]`), no new variables. A need the set can't meet is a SPEC.md §10 question for the Principal, not a new token.
7. **Responsive to 390px, and reduced motion everywhere.** Every screen works at 390px wide. **Reduced motion:** Every animated element honours `prefers-reduced-motion` (Tailwind `motion-safe:` and `motion-reduce:`): transitions become instant or crossfades, nothing moves.
8. **Accessibility.** Focus rings on keyboard focus only, an accessible name on every icon button, keyboard reach for every control, live regions for results that change while editing (the simulation's headline), and AA contrast for text. Outcome is never carried by colour alone: every outcome shows its word.
9. **Never invent Saifuro behaviour.** Every rule the engine or the copy states about mandates, verdicts, reviews or revocation cites the docs page it comes from (the `saifuro-contract` and `policy-engine` path rules hold the citations). Where the docs are silent or ambiguous, the engine picks one reading, labels it an interpretation in the rule file, and SPEC.md §10 lists it. Never present a console-only extra (approved vendors, Slack notify, the policy itself) as something the API enforces.
10. **Scope.** Build what SPEC.md lists, and nothing more. New ideas go in SPEC.md under "Later", never in code.
11. **Production is Principal-only.** No agent deploys to, changes or reads the production Vercel project, except for one command:
    - **The only Vercel command an agent may run is `vercel deploy --prod --skip-domain`.** It builds a production-target deployment and does not alias it to the production domain. Run it from a clean commit that has been reviewed, never from a dirty tree or an unreviewed branch.
    - **Everything else is denied, named or not.** That includes `vercel deploy --prod` without `--skip-domain`, `--target=production`, `promote`, `rollback`, `redeploy`, `alias`, `domains`, `link`, `pull`, `git connect`, `env` and `--prebuilt`, and any other Vercel command or flag. So are the Vercel dashboard, the Vercel API, and every change to environment variables or project settings. They are the Principal's.
    - **An unaliased build is still production.** It runs with the production environment variables and its URL is reachable. Hand the URL to the Principal in the PR and never publish it: not in the README, a comment, a commit message or the app.
    - **This rule is enforced by prose and by the Principal's Vercel project settings (SPEC.md §10), not by a permission rule.** No tool blocks a violation, so an agent that is unsure stops and asks. The detail is in the `nextjs` path rule.

## How to approach a task

- **Plan first when the task is ambiguous or spans several files.** Explore, propose the file-by-file approach, get approval, then execute. **Execute directly** for a single, well-located fix.
- **Engine work is test-first.** Write failing tests from the examples in the `policy-engine` rule, then implement.
- **When output is wrong, add a concrete input/output example** to the relevant rule rather than more prose.
- **Before stating anything about Saifuro**, find it in `spec/saifuro-openapi.yaml` or the docs page the `saifuro-contract` rule cites. If it isn't there, it isn't true.
- Finish every task with `ship-check`.

## Governance

This repo will be governed by **Vinaya**. Once it's installed, `VINAYA.md` explains the enforcement rings and roles. Work happens on branches through pull requests, never directly on `main`. Commit messages follow the format the commit-msg hook enforces.

## Working agreements

- Keep diffs small and scoped to one task.
- **A new architectural decision gets an ADR** in `docs/adr/NNNN-kebab-title.md`, in the same format as the existing ones (title and decision, *Considered options*, *Consequences*), linked from CONTEXT.md. A decision that reverses an ADR writes a new ADR; the old one is never edited.
- A new domain term goes into CONTEXT.md, with its *Avoid* list, in the same PR.
- Update SPEC.md when a decision changes. Update the relevant rule or skill when a convention changes.
- `design/` is the handoff. Its source files (`marketing-literal-palette.txt`, `docs-theme-vars.txt`, `RESEARCH-rule-uis.md`) are read-only. `design/DESIGN.md` stays a living doc: update it when a token value changes or a component is added.
- `spec/saifuro-openapi.yaml` is read-only. Replacing it is its own PR, with the regenerated `schema.d.ts` and every rule or spec line the change affects.
